# 실시간이란

실시간 = 빠름이 아니라 마감(deadline)을 지킴. 늘 같은 시간 안에 끝나는 것(결정성)이 중요하고, 우선순위 설계로 마감을 지킴

## FreeRTOS (posix · qemu-mps2 둘 다)

주기 태스크 P가 10틱마다 3틱 일하고 다음 주기 전에 끝내야 함. 응답 시간을 틱 단위로 재서 PC · QEMU 어디서나 같은 결과

```text
주기 태스크 P: 10틱마다 3틱 일함, 마감 10틱 (10번). 숫자는 응답 시간(틱), 괄호는 우선순위
1. P(3) 혼자                          : 3 3 3 3 3 3 3 3 3 3  최대 3, 마감 넘김 0
2. P(3) + 낮은 L(1)이 쉬지 않음         : 3 3 3 3 3 3 3 3 3 3  최대 3, 마감 넘김 0
3. P(3) + 높은 H(4)가 25틱마다 8틱 일함 : 3 6 3 11 4 3 6 3 11 4  최대 11, 마감 넘김 2
4. 주기가 짧은 P를 높게 P(4) · H(3)     : 3 3 3 3 3 3 3 3 3 3  최대 3, 마감 넘김 0
                                 H 응답 : 11 14 11 14  최대 14, 마감 25틱 넘김 0
```

## Linux

1ms 주기 스레드가 깨어나야 할 시각보다 얼마나 늦는지 (cyclictest와 같은 방식). 모두 CPU 0에 고정

```text
1ms 주기 스레드가 깨어나야 할 시각보다 늦은 정도 (1000번, CPU 0, 500us 넘게 늦으면 마감 넘김)
1. 일반 · 한가함                : 평균   402us, 최대   1322us, 마감 넘김 24
2. 일반 · 바쁜 스레드 2개        : 평균    70us, 최대   5069us, 마감 넘김 6
3. SCHED_FIFO · 바쁜 스레드 2개  : 평균     2us, 최대     70us, 마감 넘김 0
```

- 도커 데스크톱 VM(Linux 5.15)에서 확인. 3은 실시간 권한 필요, 없으면 "건너뜀" (권한 얻는 법은 [priority-inversion](../priority-inversion/README.md#linux-예제-조건))
- 1이 2보다 평균이 큰 것은 쉬던 CPU가 깨어나는 시간 때문. 가상 머신은 특히 큼. 실시간 시스템에서 절전 상태를 끄거나 줄이는 이유
- 숫자는 실행할 때마다 다름. 최대값이 중요해서 실제로는 몇 시간씩 잼
- Linux 전용 (CPU 고정 · SCHED_FIFO). macOS에서는 안내만 출력

## 실행

```bash
cmake --preset posix && cmake --build --preset posix
./build/posix/chapters/realtime/realtime-freertos
./build/posix/chapters/realtime/realtime-linux
```

## 바꿔 보기

| 바꿀 곳 | 결과 |
|---|---|
| FreeRTOS `H_WORK` 8 → 6 | 3번도 마감을 지킴 (`3 4 3 9 3 …`, 최대 9). 최악 응답 = P 일 3 + H 일 6 |

## 포인트

- 응답 시간 = 주기가 시작된 때부터 일을 끝낸 때까지. 평균이 아니라 최대가 마감 안이어야 함
- 결정성: 낮은 우선순위가 아무리 바빠도 높은 태스크의 응답은 그대로 (2번)
- 높은 태스크가 끼어들면 그만큼 늦음. 최악 = 내 일 + 그동안 끼어들 수 있는 높은 태스크 일 (3번 최대 11 = 3 + 8)
- rate monotonic: 주기가 짧은 태스크를 높은 우선순위로. 같은 일이라도 우선순위만 바꿔 둘 다 지킴 (4번)
- 주기 작업은 `xTaskDelayUntil`(절대 시각)로. 첫 기준 시각은 과거여야 함 (미래면 틱이 한 바퀴 돈 것으로 보고 바로 돌아옴)
- Linux 일반 정책은 공평하게 나누는 게 목적이라 가끔 수 ms 늦음. 마감이 있으면 SCHED_FIFO (24장)
