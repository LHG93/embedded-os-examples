# 종합 프로젝트: 센서 수집 → 처리 → 전송

앞에서 배운 걸 한 프로그램에 모음. 1kHz 센서 → 큐 → 처리(프레임 · 경보) → 메시지 → 전송, 그리고 감시 · 워치독

| 부분 | FreeRTOS | Linux | 배운 곳 |
|---|---|---|---|
| 센서 1kHz | TIMER0 인터럽트 → `xQueueSendFromISR` | 스레드가 절대 시각까지 잠들었다 깸 | 18 · 19 · 20장 |
| 샘플 큐 (16칸) | `xQueueCreate`, ISR이라 꽉 차면 버림 | 고리 버퍼 + 뮤텍스 + 조건 변수, 기다리지 않고 넣음 | 16장 |
| 처리 → 전송 | 메시지 버퍼 (길이가 제각각인 글자 패킷) | 큐에 구조체로 | 17장 |
| 경보 | 이벤트 그룹 비트 | 조건 변수 + 카운터 | 15장 |
| 공유 통계 | 뮤텍스 | 뮤텍스 | 11장 |
| 감시 · 워치독 | 100ms마다 "살아 있음" 비트 확인 → 진짜 워치독 킥 | 같은 감시 + 소프트웨어 워치독 스레드 | 21장 |

- 센서 값은 0.4초 주기 삼각파(0 ~ 4000) + 정해진 잡음(LCG). 그래서 두 환경의 프레임 · 패킷 · 합계가 같음
- 10샘플 = 프레임 하나(10ms). 프레임 평균이 3200을 **넘어서는 순간**에만 경보
- 지연 = 프레임의 마지막 샘플을 읽은 때 → 전송 태스크가 받은 때. 마감은 프레임 주기 10ms
- 샘플 1000개(1초)로 끝나서 지연 · 센서 주기 · 스택 여유(수십 바이트) 말고는 매번 같은 결과

## FreeRTOS (qemu-mps2 전용)

| 태스크 | 우선순위 |
|---|---|
| alarm | 4 |
| process | 3 |
| tx | 2 |
| supervisor | 1 |

```text
종합 프로젝트: 센서 1kHz → 처리 → 전송, 샘플 1000개
1. 센서 · 큐 : 샘플 1000개 보냄 · 1000개 받음, 빠짐 0개, 순서 끊김 0번, 큐 최대 대기 1개 / 16
2. 처리      : 프레임 100개 (10샘플 평균 · 최소 · 최대), 경보 3번 (평균 > 3200 넘어설 때, #016 · #056 · #096)
3. 전송      : 패킷 100개, 3009바이트, 합계 0x127a, 처음 3개는
     #000 avg=97 min=3 max=214
     #001 avg=288 min=217 max=397
     #002 avg=481 min=404 max=559
4. 지연      : 마지막 샘플 → 전송 평균 56us · 최대 1365us (마감 10000us)
5. 워치독    : 100ms마다 감시, 킥 10번 · 못 함 0번 (process · tx가 둘 다 살아 있을 때만)
6. 스택 여유 : process 1492B · tx 1812B · alarm 1868B · supervisor 1908B (각 512워드 중)
결과        : 통과
```

- 최대 지연은 거의 첫 패킷. QEMU가 처음 실행하는 코드를 번역하느라 느림 (진짜 보드엔 없는 비용)

## Linux (pthread)

```text
종합 프로젝트: 센서 1kHz → 처리 → 전송, 샘플 1000개
1. 센서 · 큐 : 샘플 1000개 보냄 · 1000개 받음, 빠짐 0개, 순서 끊김 0번, 큐 최대 대기 2개 / 16
2. 처리      : 프레임 100개 (10샘플 평균 · 최소 · 최대), 경보 3번 (평균 > 3200 넘어설 때, #016 · #056 · #096)
3. 전송      : 패킷 100개, 3009바이트, 합계 0x127a, 처음 3개는
     #000 avg=97 min=3 max=214
     #001 avg=288 min=217 max=397
     #002 avg=481 min=404 max=559
4. 지연      : 마지막 샘플 → 전송 평균 160us · 최대 632us (마감 10000us)
5. 워치독    : 100ms마다 감시, 킥 10번 · 못 함 0번 (process · tx가 둘 다 살아 있을 때만)
6. 센서 주기 : 1ms 예정보다 늦게 깨어난 최대 1017us (타이머 인터럽트가 아니라 잠들었다 깨는 방식)
결과        : 통과
```

- 센서 주기 · 지연은 실행마다 크게 다름. 도커 VM이 바쁘면 늦게 깨어남이 몇 ms까지 커짐 (한 번 7.6ms 확인). 16ms 넘게 밀리면 큐가 넘쳐 실패할 수 있음 → 24장 방법(SCHED_FIFO · mlockall)
- macOS에서도 빌드 · 실행됨. 킥은 9 ~ 10번 (마지막 확인과 끝나는 때가 겹침)

## 바꿔 보기: `SLOW_PROCESS_US`

처리 태스크가 샘플 하나마다 그만큼 더 바쁘게 돎. 두 파일 다 맨 위에 있음

| 값 | FreeRTOS | Linux |
|---|---|---|
| `900` | 빠짐 0개, 지연 최대 16 ~ 18ms → **실패 (마감 넘김)**. process(3)가 CPU를 90% 넘게 써서 tx(2)는 틈에서만 돎 | 통과 (지연 최대 ~1.3ms). CPU 하나로 묶어도(`taskset -c 0`) 통과. 공평 스케줄러라 tx도 차례가 옴 |
| `1500` | 300ms에 **워치독 리셋** (`[워치독] … 샘플 299개 중 빠짐 87개`). process가 쉬지 않아 tx · supervisor가 아예 못 돎 → 킥 끊김 | 빠짐 318개, 지연 ~25ms → 실패. 하지만 감시 · 킥은 계속됨 |

- 같은 "느린 처리"라도 FreeRTOS는 낮은 우선순위가 굶고(7장), Linux는 다 같이 조금씩 느려짐
- 고치는 방법: 처리를 가볍게, 큐를 크게(잠깐 몰리는 것만 해결), 우선순위 다시 정하기, 또는 센서를 묶어서(DMA · 여러 샘플씩) 넘기기
